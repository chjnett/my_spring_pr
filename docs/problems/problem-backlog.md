# SecureFlow 문제 백로그

## 문제를 정의하는 형식

각 문제는 답안을 쓰기 전에 아래 다섯 가지를 먼저 채운다.

| 항목 | 질문 |
| --- | --- |
| 실패 상태 | 무엇이 잘못 저장·반환·처리되는가? |
| 실제성 | SecureFlow에서 왜 이 문제가 생길 수 있는가? |
| 재현 방법 | 어떤 API·데이터·동시 요청으로 실패를 만들 수 있는가? |
| 비교 대상 | 어떤 해결책들을 비교할 수 있는가? |
| 검증 지표 | 쿼리 수, 중복 건수, 응답 코드, 처리 시간 중 무엇을 측정할 것인가? |

## 우선순위 1 — 같은 권한 요청이 여러 번 들어오면 어떻게 할까?

**상태: 완료 / 멱등성 키 TTL·실패 복구 정책은 후속 문제로 분리**

### 실패 상태

`POST /api/users/{userId}/role-grants`가 네트워크 재시도나 동시 클릭으로 여러 번 들어왔을 때, 같은 사용자에게 같은 `ADMIN` 권한 레코드가 여러 개 만들어진다.

### 왜 중요한가

권한 부여는 단순한 목록 데이터가 아니다. 중복 레코드는 감사 로그를 왜곡하고, 이후 권한 취소나 승인 흐름에서 "어느 레코드를 지워야 하는가"라는 모호함을 만든다.

### 재현 설계

1. `RoleGrant(userId, role)`를 별도 Entity로 만들었다.
2. `UNIQUE(user_id, role)` 제약이 있는 PostgreSQL에서 같은 권한 저장 요청을 20번 동시에 실행했다.
3. 저장된 권한 수와 성공 요청 수를 기록했다.

### 비교할 선택지

| 선택지 | 확인할 질문 |
| --- | --- |
| `existsByUserIdAndRole()` 후 저장 | 조회와 저장 사이의 경쟁 조건을 막을 수 있는가? |
| `UNIQUE(user_id, role)` | DB가 중복을 막은 뒤 API는 어떤 응답을 보내야 하는가? |
| Idempotency-Key | 같은 재시도는 성공 응답을 재사용해야 하는가, 409이어야 하는가? |

### 검증 지표

완료: `동시 요청 20건 / 저장 1건 / UNIQUE 충돌 19건`<br>
완료: `같은 키 동시 요청 20건 / 최초 201 1건 / 재전송 201 19건 / RoleGrant 1건 / IdempotencyRecord 1건`

## 우선순위 2 — 두 관리자가 같은 사용자의 권한을 동시에 바꾸면 무엇이 사라질까?

**상태: RoleGrant 구현 뒤 진행**

### 실패 상태

관리자 A가 `MEMBER → ADMIN`으로 바꾸는 동안 관리자 B가 `MEMBER → AUDITOR`로 바꾸면, 마지막 저장이 앞선 변경을 덮어써서 한 관리자의 의도가 사라진다. 이를 **lost update**라고 부른다.

### 재현 설계

1. 같은 권한 레코드를 두 트랜잭션에서 각각 읽는다.
2. 두 요청이 서로 다른 역할로 변경하도록 barrier를 둔다.
3. 최종 역할과 각 요청의 응답을 기록한다.

### 비교할 선택지

| 선택지 | 확인할 질문 |
| --- | --- |
| 아무 제어 없음 | 마지막 저장이 항상 이기는가? |
| `@Version` 낙관적 락 | 충돌한 요청은 어떤 예외·HTTP 응답을 받아야 하는가? |
| 비관적 락 | 충돌을 기다리게 할 때 처리 시간과 잠금 범위는 어떤가? |

### 검증 지표

`동시 수정 2건 / 성공·충돌 응답 수 / 최종 역할 / 대기 시간`

## 우선순위 3 — 권한 목록 조회가 사용자 수만큼 쿼리를 만들지는 않을까?

**상태: 관계 매핑 구현 뒤 진행**

### 실패 상태

권한 부여 목록을 조회하면서 각 권한의 사용자 정보를 접근할 때, 권한 100건에 대해 사용자 조회 SQL이 100번 추가로 나간다. 흔히 N+1이라고 부르지만, 여기서는 "관리자 권한 목록 100건 조회가 101개 쿼리를 만든다"가 문제 정의다.

### 재현 설계

1. 사용자 100명과 권한 100건을 만든다.
2. 목록 API가 사용자 이름까지 반환하도록 한다.
3. Hibernate statistics 또는 SQL 로그로 쿼리 수를 센다.

### 비교할 선택지

| 선택지 | 확인할 질문 |
| --- | --- |
| 기본 LAZY 로딩 | 실제 쿼리는 몇 번인가? |
| fetch join | 페이징·중복 row에서 어떤 한계가 있는가? |
| EntityGraph | Repository API는 얼마나 읽기 쉬운가? |

### 검증 지표

`목록 100건 조회 시 SQL 횟수 / 응답 시간 / 페이징 동작`

## 우선순위 4 — DB 저장 성공 전에 감사 로그·알림을 보내면 무슨 일이 생길까?

**상태: 권한 변경 기능 뒤 진행**

### 실패 상태

권한 부여 트랜잭션이 마지막에 롤백됐는데, 그 전에 "관리자 권한 부여 완료" 알림이나 감사 로그를 남기면 실제 DB 상태와 이벤트 기록이 달라진다.

### 재현 설계

1. 권한 부여 후 알림 이벤트를 발행한다.
2. 이벤트 발행 뒤 의도적으로 예외를 내 트랜잭션을 롤백한다.
3. 권한 레코드와 감사 로그·이벤트 기록을 비교한다.

### 비교할 선택지

| 선택지 | 확인할 질문 |
| --- | --- |
| Service 안에서 즉시 발행 | 롤백 뒤에도 이벤트가 남는가? |
| `@TransactionalEventListener(AFTER_COMMIT)` | 커밋된 변경만 관찰하는가? |
| Outbox 패턴 | 외부 메시지 전송 실패를 재시도할 수 있는가? |

### 검증 지표

`롤백 요청 수 / 잘못 발행된 이벤트 수 / 커밋 후 이벤트 수`
