# SecureFlow 백엔드 완료 판정과 후속 작업

## 결론

2026-11-02 기준으로 SecureFlow 백엔드는 **학습·포트폴리오 범위에서 완료**로 판정하고 기능 개발을 동결한다.

권한 요청부터 감사 이벤트, 외부 보안 로그 수집·검색, 규칙 탐지, 경보 처리, 관측과 성능 검증까지 하나의 제품 흐름으로 연결되어 있다. 전체 회귀 테스트와 100만 건 개발 DB 벤치마크도 완료했으므로, 새로운 백엔드 기능을 계속 추가하는 것보다 현재 설계의 근거와 한계를 설명하고 데모하는 편이 포트폴리오 가치가 높다.

이 판정은 **실서비스 운영 준비 완료**를 의미하지 않는다. 실제 배포를 결정하면 별도의 운영 보안·복구·SLO 작업을 다시 시작해야 한다.

## 완료 근거

| 영역 | 완료 증거 |
| --- | --- |
| 인증·인가 | BCrypt credential, ADMIN·AUDITOR·MEMBER RBAC |
| 권한 워크플로 | 요청·승인·거절 상태 전이, 자기 승인 차단, 낙관적 락 |
| 멱등성 | 동일 키 동시 요청에서 최초 응답 재사용과 단일 생성 |
| 감사 기록 | Transactional Outbox, `SKIP LOCKED`, retry, DLQ |
| 무결성 | HMAC v1·v2·v3 검증, 과거 키 key ring, 검색 컬럼 변조 탐지 |
| DB 신뢰 경계 | migrator/application 계정 분리, `security_events` UPDATE·DELETE 차단 |
| 로그 처리 | service credential, 최대 500건 JDBC batch, cursor 검색 |
| 탐지·경보 | 네 가지 규칙, watermark, fingerprint 중복 방지, 경보 상태 전이 |
| 관측 | Prometheus 지표와 Grafana 대시보드 |
| 검증 | 71개 자동 테스트, Docker Compose, CI·CodeQL 구성 |
| 성능 증거 | 100만 건 seed, k6 수집·검색, 세 가지 EXPLAIN ANALYZE |

성능 수치와 측정 조건은 [100만 건 벤치마크 보고서](performance-benchmark-2026-11-02.md)를 기준으로 인용한다.

## 지금 멈추는 범위

다음 항목은 포트폴리오 완료를 위해 더 구현하지 않는다.

- 새로운 탐지 규칙 추가
- API 종류 확대
- 마이크로서비스 분리
- Kafka 등 메시지 브로커 도입
- 데이터 규모를 보여주기 위한 성급한 파티셔닝
- 현재 요구가 없는 캐시 계층 추가

이 항목들은 실제 요구나 측정된 병목 없이 추가하면 설계 근거가 약해지고 프로젝트의 핵심 설명을 흐린다.

## 실제 배포 시 다시 시작할 작업

| 우선순위 | 작업 | 시작 조건 |
| ---: | --- | --- |
| 1 | KMS/Secret Manager, TLS, 네트워크 정책 | 외부 환경 배포 결정 |
| 2 | 백업·복구 훈련과 migrator 권한 통제 | 보존할 실제 데이터가 생김 |
| 3 | Prometheus Alerting Rule | 운영 당직 또는 알림 채널 결정 |
| 4 | DLQ 조회·승인·재처리 명령 | 운영자가 장애 이벤트를 처리해야 함 |
| 5 | sliding/incremental 탐지와 late-event 정책 | 8분 수준 지연이 요구사항을 만족하지 못함 |
| 6 | 규칙·threshold 정책 데이터화 | 운영 중 무배포 조정 요구가 생김 |
| 7 | 파티셔닝·보존 정책 | 수천만 건 또는 보존 기간 요구가 확인됨 |

특히 현재 10분 tumbling window의 실측 Event-to-Alert 평균은 약 8분이다. 2분 이하 탐지 SLO가 필요하다면 설정값만 조금 바꾸는 수준이 아니라 window와 재처리 정책을 함께 재설계해야 한다.

## 다음 권장 단계

백엔드 기능 추가 대신 다음 순서로 진행한다.

1. README 첫 화면에 문제, 아키텍처, 핵심 수치와 트레이드오프를 배치한다.
2. 권한 요청 → Outbox → 보안 이벤트 → 경보 조사까지 5분 데모 시나리오를 고정한다.
3. 면접 설명을 위해 동시성, 멱등성, HMAC, 100만 건 실행 계획을 자신의 말로 정리한다.
4. 필요하면 백엔드 API를 사용하는 작은 프론트엔드를 별도 단계로 시작한다.

백엔드 변경은 이후 버그 수정, 보안 취약점 대응, 실제 배포 요구가 생긴 경우에만 재개한다.
