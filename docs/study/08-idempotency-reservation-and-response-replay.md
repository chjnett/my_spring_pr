# 멱등성 선점과 최초 응답 재생 스터디

이번 구현에서 공부할 핵심은 “중복 데이터 방지”와 “같은 네트워크 작업 재생”이 서로 다른 문제라는 점이다.

## 1. UNIQUE 제약만으로 부족한 이유

권한 요청에는 같은 사용자와 역할이라도 시점과 이유가 다른 정상 요청이 있을 수 있다. 따라서 `target_user_id + role`을 무조건 UNIQUE로 만들 수 없다. 대신 클라이언트가 같은 작업을 재시도한다는 신호인 `Idempotency-Key`를 별도 저장한다.

확인 질문:

1. 비즈니스 중복과 네트워크 재시도는 어떻게 다른가?
2. 모든 POST 요청에 DB 컬럼 UNIQUE를 추가하면 어떤 정상 요청이 차단될 수 있는가?
3. 요청자 ID 없이 키만 전역 UNIQUE로 만들면 어떤 문제가 생기는가?

## 2. 사전 조회보다 원자적 INSERT가 필요한 이유

다음 코드는 경쟁 상황에서 안전하지 않다.

```text
if (!exists(key)) {
    insert(key)
}
```

두 트랜잭션이 동시에 `exists=false`를 볼 수 있기 때문이다. PostgreSQL의 `INSERT ... ON CONFLICT DO NOTHING`과 UNIQUE 제약을 함께 사용하면 DB가 한 트랜잭션에만 선점 성공을 돌려준다.

이번 구현에서는 INSERT 결과가 1이면 최초 처리자, 0이면 재시도 처리자다.

## 3. request hash가 필요한 이유

같은 키가 항상 같은 요청이라는 보장은 없다. 대상 사용자, 역할, 이유를 정규 문자열로 만든 뒤 SHA-256 hash를 저장한다.

```text
targetUserId | role | reason → SHA-256
```

저장된 hash와 새 hash가 다르면 키를 잘못 재사용한 것이므로 `422`를 반환한다. hash는 인증이나 비밀번호 보호 목적이 아니라 본문 동일성 비교를 위한 fingerprint다.

## 4. 현재 상태 조회와 최초 응답 재생의 차이

멱등성 API는 최초 작업 결과를 재생해야 한다. 생성된 요청이 나중에 승인됐다고 해서 재시도 응답까지 `APPROVED`로 바뀌면 동일 요청에 대한 응답이 시간에 따라 달라진다.

이번 모델은 생성 정보가 불변이라는 전제 아래 최초 `PENDING` 응답을 재구성한다. 다음 조건이 생기면 별도 response snapshot이 필요하다.

- 생성 이유나 대상 역할을 수정할 수 있음
- 응답 계산에 외부 시스템 데이터가 포함됨
- 법적·감사 요구로 당시 JSON 원문을 정확히 보관해야 함

## 직접 해볼 실습

1. `ON CONFLICT DO NOTHING`을 사전 `exists` 조회로 바꾸고 동시성 테스트 결과를 비교한다.
2. 같은 키로 `reason`만 바꿔 `422`가 발생하는 API 테스트를 작성한다.
3. 요청 승인 후 같은 생성 요청을 재시도해 `PENDING` 응답과 DB의 `APPROVED` 상태를 비교한다.
4. `PROCESSING` 상태에서 애플리케이션이 종료됐다고 가정하고 TTL·복구 정책을 설계한다.
5. 응답 전체를 JSON으로 저장하는 방식과 현재 ID 참조 방식을 저장 공간·호환성·정확성 관점에서 비교한다.

완료 기준은 “UNIQUE가 있으니 멱등하다”가 왜 불완전한 설명인지, 그리고 왜 키와 함께 request hash와 최초 응답 정보가 필요한지를 말로 설명하는 것이다.
